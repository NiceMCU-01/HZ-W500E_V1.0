结论：本轮全量测试 100% 通过（420/420），零失败用例。16 条 AT 指令的命令解析与响应逻辑全部 10/10 通过，固件运行稳定（10 轮全量交互零崩溃、零重启）。
本轮集中修复了 4 个缺陷，全部与上一版报告中的失败项直接相关。此前失败并非网络环境问题（已排除默认路由假设），而是固件与测试框架各自的缺陷：
① 套接字泄漏（固件）。rx_task 中对端关闭时只置 s.fd = -1 而未真正 close()；服务端模式 accept() 后又用 s.fd = c 覆盖掉 listen 套接字、使其永不释放。而 CONFIG_LWIP_MAX_SOCKETS 原本仅 8，泄漏几轮后 socket() 即返回 ENFILE(23)。已修复两处泄漏，并把上限提到 16。这正是「一开始能连上、连测几轮后全部失败」的真因。
② connect() 未等待握手完成（固件）。lwIP 的 TCP 套接字是非阻塞的，connect() 会立即返回 EINPROGRESS（lwIP 中为 115）表示「正在握手」，原代码却按 rc != 0 直接判失败 —— 于是握手其实成功、服务端也已 accept()，AT 层却回 ERROR。已改为 connect_wait()：select 等可写 + SO_ERROR 判定，并正确处理 FD_ISSET 与握手中途的 EINPROGRESS。
③ errno 残留导致误判（固件）。lwIP 在 connect() 失败时可能把 errno 留成上一次的残留值（实测出现过 118=ENOTNAM 这种无意义码），进而让 connect_wait() 误判失败。已在 connect() 前清零 errno，失败后一律以 SO_ERROR 取真实原因。
④ 测试框架三处缺陷（脚本）。这几处曾把正常行为误判为失败，现全部修正：read_until() 曾在命中应答前因静默超时提前返回，把「应答还在路上」判成失败（CIPSTART 实测要7s 才应答，误报率可达 100%）；AT+CWJAP 之后未等待 STA 真正拿到 IP 就发后续网络命令，而该命令只是发起连接、关联与 DHCP 由后台任务完成；is_ok() 曾要求 OK 必须是应答末尾，但 HTPC / 透传在 OK 之后还会追加 CLOSED 等异步通知行，属正常行为却被判失败。
此外，HTPC 在 connect 前设置 SO_RCVTIMEO/SO_SNDTIMEO 会导致连接稳定失败，已移除并改用 select 控制读取超时，同时给 HTTP 加上连接重试以容忍 TIME_WAIT 占用的套接字额度。
累计修复固件缺陷 9 个：① esp_wifi_connect() 阻塞 AT 命令任务；② 自触发断线重连死循环；③ STA 的 DHCP 客户端从未启动；④ CWJAP? 输出未限长导致 SSID 为空；⑤ CIPSEND 逐字节发送使 UDP 拆成N 个单字节报文；⑥ 重连风暴导致 AP 拉黑 MAC（指数退避修复）；⑦ 套接字泄漏 + 上限过小；⑧ connect() 未等待握手完成；⑨ errno 残留导致误判。
诊断方法：因 AT 固件不能开日志（日志会污染应答），新增 +CIPERR,<stage>,<errno> 诊断行随应答输出（stage：1=socket 2=connect 3=bind 4=listen 5=send），ENFILE(23) 与 118 两个关键线索均由它定位。
